Query Optimizer

Statistics, estimates, rewrites, and choosing among plans

A logical plan in, a physical plan out. The logical plan says join. You decide which join, in what order, over which access paths, and you decide it from numbers you computed rather than from the order the user happened to type.

This module is also where you learn that the numbers lie. Half the marks sit in the part of the report where you show your own optimizer being wrong.
1  Statistics

Computed by an ANALYZE command that scans the table once and stores the result in the catalog from Module 1. Compute exactly. No sampling, so that your numbers are reproducible and checkable.
Statistic 	Meaning
n_tuples(T)	Live tuples in the table.
n_pages(T)	Data pages, excluding directory pages.
width(T)	Average record length in bytes.
ndv(T.c)	Number of distinct values in the column.
min(T.c), max(T.c)	Lowest and highest value.
hist(T.c)	Equi-depth histogram, k buckets, each holding its value range, its tuple count and the number of distinct values inside it.

Equi-depth means every bucket holds roughly the same number of tuples, so bucket boundaries are close together where data is dense. Build it by sorting the column and cutting at every n/k-th value. Bucket count k is set by --buckets and defaults to 20. The sort must use your external sort from Module 2, because ANALYZE on a large table cannot hold the column in memory.
2  Selectivity

Selectivity is the fraction of input tuples a predicate keeps, between 0 and 1. These are the required default formulas. You may improve on them, and several are worth improving, but your design document must state what you implemented and why.
Predicate 	Selectivity
c = v	Find the bucket holding v. Selectivity is count(bucket) / (n_tuples × ndv(bucket)). With no histogram, 1 / ndv(c).
c < v, c > v	Sum whole buckets on the correct side, plus a linear fraction of the bucket containing v.
c <> v	1 − sel(c = v)
p AND q	sel(p) × sel(q). This assumes independence, which is the assumption you will later break on purpose.
p OR q	sel(p) + sel(q) − sel(p) × sel(q)
NOT p	1 − sel(p)
R.a = S.b (join)	Output rows are n(R) × n(S) / max(ndv(R.a), ndv(S.b)).
Any other join predicate	Selectivity 0.1 by default. Say so in your document rather than hiding it.

Output cardinality of a node is the input cardinality times the selectivity, rounded up, never below 1. Output pages are ceil(rows × width / 4096), which is how a projection that drops columns reduces later costs.

Worked example. Emp has 10,000 tuples on 200 pages. ndv(did) = 50, age runs from 20 to 70 uniformly. Dept has 50 tuples, ndv(did) = 50.

did = 7            sel = 1/50  = 0.02   ->   200 rows
age > 60           sel = 10/50 = 0.20   ->  2000 rows
did = 7 AND age>60 sel = 0.004          ->    40 rows
Emp JOIN Dept on did    10000 * 50 / max(50,50) = 10000 rows

That last line is worth pausing on. Joining every employee to their department returns one row per employee, which is exactly 10,000. The formula gets it right here because did is a key of Dept. It will not always be this kind.
3  Rewrite rules

Applied to the logical plan before costing. Each rule has a precondition, and a rule applied where its precondition fails produces wrong answers rather than slow ones.
# 	Rule 	Precondition
1	Split conjunctions. select[p AND q] becomes two stacked selects.	None. Always safe, and it is what makes rule 2 possible.
2	Push a select below a join or cross.	The predicate references columns from one side only. Push it to that side.
3	Turn cross plus select into join.	The predicate references both sides and is an equality. This is what makes a comma join as good as a JOIN ON.
4	Push a select below a rename, union or union_all.	Rewrite column names through the rename. For unions, push into both branches.
5	Push a select below a group_by.	Only if the predicate references grouping columns alone. A predicate on an aggregate can never move. This is HAVING against WHERE seen from the other direction.
6	Push projections down.	Insert a projection below an operator keeping only columns its ancestors need, plus the ones that operator needs itself. Never drop a column a predicate above still references.
7	Remove a projection that drops nothing, and collapse adjacent selects.	Cosmetic, but it makes your explain output readable.

Worked example. The comma join from Module 3, before and after.

SELECT e.name FROM Emp e, Dept d
 WHERE e.did = d.did AND e.age > 60 AND d.budget > 1000;

before                              after
project [e.name]                    project [e.name]
  select e.did=d.did                  join e.did=d.did
    select e.age>60                     project [e.name,e.did]
      select d.budget>1000                select e.age>60
        cross                               rename e (scan Emp)
          rename e (scan Emp)             project [d.did]
          rename d (scan Dept)              select d.budget>1000
                                              rename d (scan Dept)

Three rules fired. Rule 1 split the conjunction, rule 2 pushed the two single-sided predicates to their own sides, rule 3 converted the cross into a join. Rule 6 then added the two projections. Your explain must be able to show both trees, because your report needs the comparison.
4  Cost model

Cost is page I/O, reads plus writes. CPU is ignored. M and N are estimated page counts of the inputs, and B is the memory budget.

seqscan                M
filter, project        0            pipelined, no I/O of its own
sort                   2 * M * (passes - 1) + M
                       passes = 1 + ceil( log(ceil(M/B)) / log(B-1) )
distinct, group_by     cost of the sort or of the hash partitioning it uses
nested_loop_join       M + ceil(M / (B-2)) * N
sort_merge_join        sort(M) + sort(N) + M + N
hash_join              3 * (M + N)
limit                  0

These must match the formulas in Module 2, because your report compares the cost your optimizer predicted against the I/O your executor actually performed. If the two modules disagree about what a hash join costs, say which is right and fix the other.
5  Join enumeration

Dynamic programming over left-deep trees, in the style of Selinger. Up to six relations.

best[{r}] = the cheapest access path for r alone, for every relation r

for size k = 2 .. n:
    for every subset S of the relations with |S| = k:
        best[S] = min over r in S, over each join algorithm A, of
                      cost( best[S - {r}]  A-join  best[{r}] )
        skip any pairing with no join predicate between S-{r} and r,
            unless no alternative exists

answer = best[all relations]

Left-deep means the right input of every join is a base relation, never another join. Your design document must say what that restriction gives up and what it buys. The honest answer involves the size of the search space and the fact that a left-deep tree can pipeline its outer side.
5.1  Worked example

Three relations, B = 32. A is 100 pages and 5,000 tuples, B′ is 10 pages and 500 tuples, C is 400 pages and 20,000 tuples. Predicates are A.x = B'.x with 1,000 estimated output rows, 20 pages, and B'.y = C.y with 2,000 output rows, 40 pages. There is no predicate between A and C.
Subset 	Best plan considered 	Cost
{A}	scan A	100
{B′}	scan B′	10
{C}	scan C	400
{A,B′}	B′ outer, BNL with A inner, 10 + 1×100	110
{B′,C}	B′ outer, BNL with C inner, 10 + 1×400	410
{A,C}	no predicate, skipped	—
{A,B′,C}	{A,B′} outer (20 pages), BNL with C inner, 110 + 20 + 1×400	530
 	alternative, {B′,C} outer (40 pages), BNL with A inner, 410 + 40 + 100	550

The winner joins the small relation to A first, which keeps the intermediate result small enough to fit in B − 2 frames and makes the second join a single pass over C. Your dp-table command prints exactly this table for any query, which is how you debug the optimizer and how I check that it enumerated rather than guessed.
6  Output and interface

opt analyze  --db DIR --table R [--buckets 20]
opt plan     --db DIR --logical q.json --frames 32 --json    // physical plan
opt explain  --db DIR --logical q.json --frames 32
opt dp-table --db DIR --logical q.json --frames 32

explain output, one line per node
hash_join (R.b = S.b)        est_rows=2000   est_cost=330
  filter (R.a > 500)         est_rows=1000   est_cost=0
    seqscan R                est_rows=10000  est_cost=200
  seqscan S                  est_rows=500    est_cost=10

The physical plan must be valid input to your Module 2 executor with no editing. That is the test of this module more than any number in the report.
7  Required measurements

Estimation quality. For the twenty supplied queries, record estimated and actual rows at every node. Report q-error, the larger divided by the smaller, with the median and the worst case across all nodes. A median near 1 is good. A worst case in the hundreds is normal and is the interesting part.

Does optimization pay. For each query, measure the actual I/O of your chosen plan and of the unoptimized plan, meaning joins in written order with one fixed algorithm and no pushdown. Report the ratio per query and the range across the workload.

Which rule mattered. Turn off one rewrite rule at a time and rerun the workload. One row per rule, giving total I/O with and without it. Some rules will turn out to be worth almost nothing on this data. Say which, and say why.

Where it breaks. Two columns in the supplied dataset are strongly correlated, which means rule 2's independence assumption is false for predicates on both of them. Find a query where this makes your optimizer choose a bad plan. Give the estimate, give the actual, name the assumption that failed, and measure what the bad plan cost against the better one. Then describe what statistic would have prevented it.

This last item carries more marks than the other three together. An optimizer that is never wrong on a workload I designed to break it has not been tested.
